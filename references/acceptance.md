# Acceptance checks

Record the actual surface, viewports, and states inspected. A documentation edit is not a verified application improvement.

| Area | Observable check |
| --- | --- |
| Main task | A first-time reader can find the relevant records and the primary action without reading an introductory paragraph. |
| Spacing | Related elements are closer than separate tasks. Computed margins and padding do not accidentally double the intended gap. |
| Density | Short summaries have no unexplained fixed-height blank space; ordinary data remains readable at normal zoom. |
| Hierarchy | The page has one clear primary action, consistent section labels, and an appropriate number of work surfaces. |
| Data | Comparable numbers align; long values remain accessible; status is understandable without relying on color alone. |
| Interaction | Hover, keyboard focus, selection, disabled, and progress states match real behavior. Static cards are not presented as clickable. |
| Narrow layout | Toolbars wrap, fields remain usable, and only genuinely wide data regions scroll horizontally. |
| Recovery | Initial loading, refresh, empty results, and errors preserve context and provide an appropriate next step. |
| Implementation | The change reuses the existing styling system and passes the checks relevant to that project. |

When comparing two layouts, keep content, viewport, filters, and data volume equal. Report specific visible differences rather than inventing a productivity percentage. Compactness alone is not a usability test: more visible rows are useful only when the text, targets, and task remain clear.

Use one batched visual inspection, fix the material findings, and confirm in a second pass if needed. Do not turn a bounded refinement into endless cosmetic changes.
